# Computer use — full plan and implementation (22 September 2026)

## Decision

Muse Desktop does **not** implement desktop control. It **embeds cua-driver** (the open-source project [trycua/cua](https://github.com/trycua/cua), MIT) as its engine, adopts its "app-hosted service" architecture, and adds only what the driver does not have: **a single consent surface**, a **capability manifest** the application generates and approves, and the **agent wiring** through MCP.

What that replaces: the application list (`browser`, `finder`, `terminal`, `editor`) of which three entries were read by no code, and a native `desktop_control.rs` that could only observe and click, without the agent being able to use it.

## What is measured on this machine (driver 0.28.2)

| Fact | Measurement |
|---|---|
| Driver installed and healthy | `cua-driver doctor --json` → `ok: true`: binary, `interactive session` (session 1, desktop attached), `UI Automation` (`CoCreateInstance(CUIAutomation)` OK), 15 windows |
| Tool surface | `cua-driver list-tools` → **76 tools** (desktop, CDP browser, clipboard, recording, sessions, agent cursor) |
| MCP invocation | `cua-driver manifest` → `mcp_invocation = ["<…>\cua-driver.exe", "mcp"]` |
| Private daemon on a named channel | `cua-driver serve --socket \\.\pipe\muse-cp` → `daemon is running`, `call get_screen_size` → `{"width":1920,"height":1080,"scale_factor":1.0}` |
| Bounded mode **enforced by the driver** | manifest `{"version":1,"mode":"bounded","expires_after":"1h","idle_timeout":"15m","allow":{"tools":["get_screen_size"]}}` → `permission mode: bounded (trusted_startup_configuration)`, `capability manifest: configured=true, approved_at_startup=true, valid=true` + **sha256**; `get_screen_size` passes, `list_windows` returns **`Permission denied: tool 'list_windows' is outside the capability manifest`** |
| Administrator rights | not required (documented and observed) |
| Licence | MIT, no commercial restriction (the `cua-agent[omni]` path pulls AGPL ultralytics — **out of scope**, we only use the driver) |

## Architecture

```
Muse Desktop (Tauri, interactive session, owner of the consent)
  │
  ├─ 1. starts its own service ONCE, on a named channel of its own:
  │      cua-driver serve --socket \\.\pipe\muse-desktop-computer
  │                     --permission-mode bounded
  │                     --capability-manifest <manifest generated by the app>
  │                     --approve-capability-manifest
  │      (mode and manifest fixed for the life of the process; the agent cannot widen them)
  │
  ├─ 2. UI: a "Computer use" switch, the driver's state, a summary of the
  │      permissions, the manifest's sha256, and Revoke.
  │
  └─ 3. agent wiring: the Muse host receives, in `config.mcpServers`:
         { transport: "stdio", command: <cua-driver.exe>, args: ["mcp", "--socket", <channel>] }
         → the agent calls click / type_text / get_window_state / … (76 tools)
```

Why a daemon rather than one `cua-driver mcp` per session: the driver's documentation is explicit — **each `mcp` without `--socket` owns its own runtime**, instances share nothing, and "do not rely on ambient discovery". One daemon, one channel, several MCP sessions: this is the "App-hosted service" model CUA documents for a signed desktop application serving an external agent.

Why the manifest is ours: the driver "renders neither an authorization modal nor a banner". Consent is therefore our job — and that is exactly what the measurement above makes possible cleanly, since the driver **itself refuses** any tool outside the manifest.

## Plan

### Phase A — the switch (UI, depends on no binary)

- The Desktop panel becomes **Computer use**: a switch, not an application list.
- What it shows: driver state (absent / version / healthy), the interactive session, the number of granted tools, the manifest's sha256, and **Revoke**.
- Three levels, not 76 checkboxes:
  1. **Observe** — screenshots, windows, accessibility tree (read only).
  2. **Observe and act** *(default)* — adds mouse, keyboard, windows.
  3. **Everything** — adds clipboard, CDP browser and recording, with an explicit warning about the clipboard.
- The `finder`, `terminal` and `editor` toggles disappear: no code read them. The `browser` grant stays, but **where it is enforced** (the Browser panel), and is renamed so it is no longer confused with Computer use.

### Phase B — the native service (`src-tauri/src/computer.rs`)

- `computer_status`: finds the binary (PATH then `%LOCALAPPDATA%\Programs\Cua\cua-driver\bin`), reads `--version`, `doctor --json`, `list-tools`, and the state of **our** channel.
- `computer_enable(level)`: writes the manifest into the app's data folder, starts the daemon on the private channel, verifies through `status --socket` (mode, approved manifest, sha256).
- `computer_disable`: `revoke --all --socket` then `stop --socket`.
- `computer_manifest`: the current manifest, so the UI can show what is granted.
- None of this accepts a path or an argv coming from the renderer: the channel, the binary and the arguments are built in Rust, as they are for `muse_auth`.
- Installing the driver is **not silent**: if the binary is missing, the app shows the official command and copies it. Downloading and running a remote script is a supply-chain decision, not an implementation detail.

### Phase C — wiring the agent

- A `computerUseMcpServer(status)` helper produces the stdio entry, merged into `buildHostMcpServers` when the switch is on.
- Effect: **new conversations** and **resumed conversations**. The panel offers "Apply to this conversation" (a resume), because the MCP list is fixed at `session/start`/`session/resume`.
- The agent does **not** start a second service: it receives a channel, not a binary to launch.

### Phase D — approvals and honesty

- The ceiling is the manifest (driver); gesture-by-gesture approval stays the Muse host's (the conversation's approval mode), to be verified.
- The copy says what the sandbox does not cover: **mouse and keyboard actions leave the workspace**; Muse's sandbox protects the folder, not the desktop.
- The driver's agent cursor is visible on screen: that is the honest counterpart of an agent that acts.

### Phase E — verification

- Pure Rust tests: manifest construction (levels → tool lists), parsing of `doctor`/`status`, structural guard on the payload returned to the renderer.
- Live script: enable → check `status` (bounded mode, approved manifest) → call an allowed tool and a refused one → check that the session's `config.mcpServers` contains the driver → disable → check it stopped.
- UI probe: a single switch, no application list, readable state.

## Explicitly out of scope

- Installing the driver on the user's behalf (see Phase B).
- CUA's VMs and sandboxes (`Image.windows()`, Lume, Docker): that is the other half of the project, for disposable computers. Here the user wants **their** machine.
- `cua-agent`/`cua-computer` (Python): the agent is Muse. We wire only the driver.
- macOS/Linux: the driver covers them, but nothing will be claimed without a measurement. `doctor` will say `supported: false` where it is not true, as `desktop_control.rs` already did.

## Status: phases A, B and C delivered and verified (22 September 2026)

`node scripts/ux-computer-use.mjs` against the live application:

```
initial state  {"driverVersion":"cua-driver 0.28.2","available":true,
                "levels":{"observe":19,"control":38,"everything":57},
                "grantState":"stopped","unclassified":[]}
enable         {"grantState":"active","tools":19,"digest":"65892b621c3d1839"}
MCP entry      {"transport":"stdio","command":"…\\cua-driver.exe",
                "args":["mcp","--socket","\\\\.\\pipe\\muse-desktop-computer"]}
enforcement    get_screen_size → { "height": 1080, "width": 1920 }
               click           → Permission denied: tool 'click' is outside the capability manifest
revoke         {"grantState":"stopped"} — manifest withdrawn
```

Verdict: `PASS`. What is proved, in the order that matters:

1. the driver is found, versioned and probed **by Rust** (7 `doctor` probes returned to the renderer);
2. the three levels map onto the driver's real surface (19 / 38 / 57), with **no unclassified tool**;
3. enabling starts a bounded service with **our** manifest, and **the driver is what enforces it**: `get_screen_size` answers, `click` is refused;
4. the MCP entry handed to the host targets **our own named channel**, and disappears as soon as the grant is no longer active;
5. revoking stops the service and withdraws the manifest.

What is not proved yet: a real turn where **the model** calls a `computer_*` tool (that needs a conversation and credits), and applying a level change to an already-open conversation — the MCP list is fixed at `session/start`/`session/resume`, so a resume is needed.

## Known risks, measured or documented

| Risk | Handling |
|---|---|
| A non-interactive session (Session 0, a service, SSH) does not see the desktop | `doctor` says so; the app refuses to enable and shows the reason |
| Two concurrent runtimes share nothing | one channel, owned by the app, never ambient discovery |
| Simultaneous sessions: shared screen, keyboard and focus | to document in the UI; a drag must not be split across two calls |
| The grant expires mid-way | `expires_after`/`idle_timeout` are app constants, displayed; the real effect is measured in Phase E |
| Background Chromium/Electron, elevated apps | structured `background_unavailable` refusal from the driver; relayed as is |
