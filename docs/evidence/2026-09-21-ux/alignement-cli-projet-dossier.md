# Alignement sur le modèle du CLI — projet, dossier, règles (21 septembre 2026)

Question posée : « comment ça marche au niveau du CLI, est-ce qu'un projet égale un dossier ? » Réponse : **côté CLI, oui — et c'est notre client qui a divergé.** Ce document établit les deux modèles, mesure l'écart, et corrige ce qui était corrigeable sans refonte.

## Côté CLI : un projet EST un dossier

Trois vérifications convergentes.

**1. Le CLI n'a aucune notion de « projet ».** Son vocabulaire est uniquement spatial : `--workspace <PATH>`, `--trust-workspace`, « workspace tools », « workspace shell ». Aucune commande, aucun flag, aucun concept de projet.

**2. `muse init` écrit un `AGENTS.md` dans le dossier**, et le dit lui-même :

```
# AGENTS.md

Muse Code reads this file as project rules when it runs in this directory.

## Project
- Name: muse-init-probe-558310543
- Generated by `muse init`.
```

Le nom du projet est **dérivé du nom du dossier**. Les règles vivent donc avec le code, versionnées avec lui — c'est la convention `agents.md`, que Claude et Codex partagent.

**3. Le schéma MSP n'expose qu'une chose : `workspaceRoot`, un chemin.** Toutes les occurrences relevées dans `msp.d.ts` sont `workspaceRoot: string` (ou `string | null`). Aucun `projectId`. Les règles du dossier ne sont même pas lisibles par le client : elles ne sont pas dans le contrat.

## Côté client : un projet est une entité séparée

| | CLI | Notre client |
|---|---|---|
| Nature du projet | **le dossier lui-même** | entité `Project` avec un `id` |
| Instructions | **`AGENTS.md` dans le dossier** | champ `instructions` en `localStorage` |
| Dossiers par projet | **un** | `workspace` **+** `workspaces[]` |
| Visibilité | lue par le host | **invisible au client** |

D'où la confusion signalée sur l'écran de démarrage : « Change folder · openscreen » et « Start in — Default workspace · openscreen » affichent **le même texte** alors que le premier choisit un dossier et le second un jeu de réglages. Le couplage est de surcroît bidirectionnel : choisir un projet écrase le dossier, changer de dossier remet le projet à `default`.

## L'écart qui comptait vraiment

**Le client ne lisait jamais `AGENTS.md`** — zéro référence dans tout le code — et surtout :

**`--trust-workspace` n'était jamais passé à `muse serve`.** Vérifié : zéro occurrence de « trust » dans le bridge Rust.

Or ce flag est ce qui fait lire les règles et les skills du dossier. **Mesuré**, sur un dossier de test contenant une skill de projet :

| | Skills découvertes |
|---|---|
| `muse skills list --source all --workspace <tmp>` | **52** |
| … avec `--trust-workspace` | **53** |

**Le flag change donc réellement la découverte** : sans lui, les règles et skills du dossier sont ignorées en silence. Un utilisateur pouvait écrire un `AGENTS.md` de 23 Ko et n'avoir aucun effet, sans le moindre message.

Une première comparaison sur `G:\repos\openscreen` avait donné `[]` des deux côtés — **non concluante** : ce dossier n'a pas de skill de projet à découvrir. Une différence de zéro ne prouve rien ; il fallait un dossier qui en contient.

## Ce qui a été corrigé

`--trust-workspace` est ajouté dans `HostSandboxPolicy::cli_args`, le point unique qui alimente **tous** les lancements de host. Il s'applique donc aux trois postures (workspace, network, elevated) sans duplication.

**Vérifié à deux niveaux :**
- test Rust `every_sandbox_posture_trusts_the_workspace`, qui échoue si une posture cesse de le passer — une régression ici rendrait les règles à nouveau muettes, sans erreur nulle part ;
- lecture de la ligne de commande du host vivant : `serve --trust-workspace : OUI`.

Tests : **209 Rust, 1091 Node, 0 échec**. Build vert.

## Reste à faire, dans l'ordre de valeur

1. **Lire et afficher le `AGENTS.md` du dossier** à la sélection — en lecture seule, pour montrer les règles qui existent réellement. Le client ne les voit pas aujourd'hui.
2. **Écrire nos instructions de projet dans `AGENTS.md`** au lieu de `localStorage` (décidé, pas encore fait). Supprime le doublon de deux jeux d'instructions qui s'ignorent.
3. **Supprimer `workspaces[]`** : un projet = un dossier, comme le CLI. Le multi-dossier n'a aucun équivalent backend.
4. **Renommer « Start in »** en « Project settings », et n'afficher que ce qui distingue.
5. **Une case worktree au démarrage** — la plomberie existe (`git_worktree_create_session` crée le worktree, démarre la session dedans et le nettoie en cas d'échec), mais elle exige une session parente. Il faut une variante sans session, puis la case dans l'interface.

## La leçon

Nos concepts « projet » et « dossier » ne sont pas faux en soi — ils répondent à un besoin réel (regrouper des conversations, hériter des réglages). Mais ils **ne correspondent à rien dans le backend**, et cette divergence a produit deux effets concrets : une interface qui juxtapose deux vocabulaires pour une seule réalité, et un flag manquant qui rendait les règles du dossier silencieusement inopérantes.

**S'aligner sur le backend n'est pas renoncer à nos concepts** : c'est vérifier que ce qu'on invente par-dessus a un fondement, et que ce qu'on omet a des conséquences.
