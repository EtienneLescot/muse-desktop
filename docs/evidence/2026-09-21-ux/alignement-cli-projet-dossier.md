# Aligning with the CLI's model — project, folder, rules (21 September 2026)

The question asked: "how does it work in the CLI — does a project equal a folder?" The answer: **on the CLI side, yes — and it is our client that diverged.** This document sets out both models, measures the gap, and fixes what could be fixed without a redesign.

## On the CLI side: a project IS a folder

Three converging checks.

**1. The CLI has no notion of "project".** Its vocabulary is purely spatial: `--workspace <PATH>`, `--trust-workspace`, "workspace tools", "workspace shell". No command, no flag, no project concept.

**2. `muse init` writes an `AGENTS.md` into the folder**, and says so itself:

```
# AGENTS.md

Muse Code reads this file as project rules when it runs in this directory.

## Project
- Name: muse-init-probe-558310543
- Generated by `muse init`.
```

The project's name is **derived from the folder's name**. The rules therefore live with the code, versioned with it — the `agents.md` convention, which Claude and Codex share.

**3. The MSP schema exposes only one thing: `workspaceRoot`, a path.** Every occurrence found in `msp.d.ts` is `workspaceRoot: string` (or `string | null`). No `projectId`. The folder's rules are not even readable by the client: they are not in the contract.

## On the client side: a project is a separate entity

| | CLI | Our client |
|---|---|---|
| Nature of a project | **the folder itself** | a `Project` entity with an `id` |
| Instructions | **`AGENTS.md` in the folder** | an `instructions` field in `localStorage` → **removed** |
| Folders per project | **one** | `workspace` **+** `workspaces[]` |
| Visibility | read by the host | **read-only probe** (`rules_scan`) |

Hence the confusion reported on the start screen: "Change folder · openscreen" and "Start in — Default workspace · openscreen" show **the same text** although the first picks a folder and the second a set of settings. The coupling is moreover two-way: picking a project overwrites the folder, changing folder resets the project to `default`.

## The gap that really mattered

**The client never read `AGENTS.md`** — zero references in the whole codebase — and above all:

**`--trust-workspace` was never passed to `muse serve`.** Verified: zero occurrences of "trust" in the Rust bridge.

Yet that flag is what makes the folder's rules and skills get read. **Measured**, on a test folder containing a project skill:

| | Skills discovered |
|---|---|
| `muse skills list --source all --workspace <tmp>` | **52** |
| … with `--trust-workspace` | **53** |

**The flag therefore really changes discovery**: without it, the folder's rules and skills are silently ignored. A user could write a 23 KB `AGENTS.md` and have it take no effect, without the slightest message.

A first comparison on `G:\repos\openscreen` had given `[]` on both sides — **inconclusive**: that folder has no project skill to discover. A difference of zero proves nothing; a folder that contains one was needed.

## What was fixed

`--trust-workspace` is added in `HostSandboxPolicy::cli_args`, the single point feeding **every** host launch. It therefore applies to all three postures (workspace, network, elevated) with no duplication.

**Verified at two levels:**
- the Rust test `every_sandbox_posture_trusts_the_workspace`, which fails if a posture stops passing it — a regression here would make the rules silent again, with no error anywhere;
- reading the live host's command line: `serve --trust-workspace: YES`.

Tests: **209 Rust, 1091 Node, 0 failures**. Build green.

## What remains, in order of value

1. **Read and display the folder's `AGENTS.md`** on selection — read only, to show the rules that really exist. **Done** (`rules_scan`, `src/lib/harnessRules.ts`), see `regles-du-dossier.md`.
2. ~~**Write our project instructions into `AGENTS.md`** instead of `localStorage`.~~ **Abandoned, and it was the right decision**: the user's `AGENTS.md` belongs to them, and it is the CLI's job to write it (`muse init`, `/rules import`). The duplicate was indeed removed — but the other way round: it is our client field that disappears, not the file that becomes our storage.
3. **Remove `workspaces[]`**: one project = one folder, as in the CLI. Multi-folder has no backend equivalent.
4. ~~**Rename "Start in"** to "Project settings", and display only what distinguishes.~~ **Done**, under the name **"Project"**: the control *picks* a project, it does not edit it — "settings" would have lied the other way. The default option becomes "No project", and the folder is displayed only when it teaches something (`projectOptionLabels`), which removes the "openscreen · openscreen" shown under a folder picker already saying "openscreen". The Projects panel's `Start in` stays: there, it really does designate a folder.
5. **A worktree checkbox at start** — the plumbing exists (`git_worktree_create_session` creates the worktree, starts the session inside it and cleans up on failure), but it requires a parent session. A session-less variant is needed, then the checkbox in the interface.

## The lesson

Our "project" and "folder" concepts are not wrong in themselves — they answer a real need (grouping conversations, inheriting settings). But they **correspond to nothing in the backend**, and that divergence produced two concrete effects: an interface juxtaposing two vocabularies for a single reality, and a missing flag that made the folder's rules silently inoperative.

**Aligning with the backend is not giving up our concepts**: it is checking that what we invent on top has a foundation, and that what we omit has consequences.
