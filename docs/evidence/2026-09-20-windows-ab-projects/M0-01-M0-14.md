# Isolation A/B entre deux projets — M0-01 / M0-14 (20 septembre 2026)

Campagne CDP sur la version de développement, sidecar Muse Windows natif 1.3.0.
Complète [`../2026-09-20-windows-group1/README.md`](../2026-09-20-windows-group1/README.md).

## Mode opératoire

```powershell
$env:WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS = "--remote-debugging-port=9222"
npm run tauri -- dev
node scripts/cdp-ab-projects.mjs --declare --live
```

## Ce que le scénario ajoute

Le profil ne déclarait qu'**un seul projet** (`openscreen`), alors que les sessions couvraient déjà deux workspaces. Le sélecteur « Start in » ne proposait donc qu'une racine, et le scénario « deux projets » du texte de M0-01 n'était pas reproductible.

Un **second projet** a été déclaré dans `muse-desktop.projects.v1`, pointant sur `C:\Users\etien\Documents\repos\muse-desktop`, avec l'accord explicite de l'utilisateur. Le script ne mute cet état que sous `--declare`.

## Résultat mesuré

| Étape | Observation |
|---|---|
| Avant déclaration | 1 projet (`openscreen`), sélecteur à 2 options issues de ce seul projet |
| Déclaration + rechargement | **2 projets** : `openscreen`, `muse-desktop` |
| Sélecteur | 3 options : `Default workspace · openscreen`, `openscreen · openscreen`, **`muse-desktop · muse-desktop`** |
| Conversation démarrée sur la 2ᵉ racine | `ab-project-abt2xyhw:0`, message envoyé, `connected: true`, `working: true` |
| Workspaces en session | **3 distincts** : `muse-dogfood`, `G:\repos\openscreen`, `repos\muse-desktop` |
| Hosts `muse serve` | **2 → 3** : un host neuf (`PID 35576`, 15:29:43) a été créé pour le nouveau workspace |

### Le test d'isolation

Le host du second projet (`PID 35576`) a été tué. État relevé **dans la même application**, sans redémarrage :

| Conversation | Projet | État après la mort du host |
|---|---|---|
| « Reply with just the word ISOLATED and nothing else. » | muse-desktop | **`Disconnected`** — « host process ended. Reconnect to continue. » |
| « Enumerate the three Musketeers by name. » | openscreen | **`Connected`** |

Autres mesures au même instant : **64 sessions conservées**, application `Responding: True`, hosts restants `46932` et `18764`, **aucun respawn**.

## Conclusion

**Établi :**

- un **host par workspace** : ouvrir une conversation dans un second projet crée un troisième processus `muse serve` ;
- la mort d'un host **n'affecte que les conversations de son workspace** ; les conversations des autres projets restent `Connected` ;
- l'application ne redémarre pas, ne perd aucune session et ne relance aucun host silencieusement.

**Non établi — et je ne le présente pas comme acquis :**

- le test est **séquentiel** : la conversation `openscreen` a été vérifiée *après* la mort du host, pas pendant qu'un tour s'y exécutait. Le critère « A continue à travailler pendant que B meurt » n'est donc pas démontré ;
- **aucune approbation simultanée** n'a été exercée : c'est le critère explicite de M0-01 qui reste ouvert ;
- la mort du host a été provoquée par `Stop-Process` sur un PID identifié par sa date de création, pas par un arrêt contrôlé depuis l'interface.

## Note d'environnement

Le second projet a été déclaré dans `muse-desktop.projects.v1` et **reste déclaré** après la campagne. C'est un état persistant du profil local, pas une modification du dépôt.
