## 1. NSIS installer build

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/build-windows.ps1 -Bundle nsis
```

The script chains `npm run build` (frontend), `npm run tauri -- build --bundles nsis`, then generates and **verifies** the manifest. **Output: exit code 0.**

| Artefact | Size | SHA-256 |
|---|---|---|
| `nsis/Muse-Desktop_0.1.0_x64-setup.exe` | **75,617,763 bytes** (72.11 MiB) | `c8fcb5da1c2f49c3527e83e9f4791c068811a2fc8e45d67c439294221a6c30bd` |
| `nsis/Muse-Desktop_0.1.0_x64-setup.manifest.json` | — | schema `muse-desktop.release-manifest.v1` |

**Independent checks:**

- SHA-256 **recomputed** afterwards: identical to the manifest's;
- `verify-release-manifest.mjs` re-run by hand against the real bytes → `{"valid": true, "errors": []}`;
- the executable's Windows metadata: `FileDescription: Muse-Desktop`, `ProductName: Muse-Desktop`, `FileVersion: 0.1.0`, `ProductVersion: 0.1.0`;
- `CompanyName` **empty**;
- **Authenticode signature: `NotSigned`.**

The manifest carries the installer **and** the sidecar with their sizes and fingerprints, with no machine path and no timestamp. Since the sidecar is not versioned, this manifest ties the installer produced to the binary the build environment actually supplied — which is exactly its role.

## 2. Differential update chain

Tested end to end on a realistic case: the real installer, then the same file with a 29-byte tail added (simulating a new build).

```powershell
node scripts/release-delta.mjs create --from old.bin --to new.bin --output update.delta.gz
node scripts/release-delta.mjs apply  --from old.bin --patch update.delta.gz --output rebuilt.bin
```

| Measurement | Value |
|---|---|
| Source | 75,617,763 bytes |
| Target | 75,617,792 bytes |
| **Delta produced** | **59,126 bytes (57.7 KB)** |
| Blocks changed | **1 out of 1154** |
| `useDelta` | `true` |
| Rebuilt file | **75,617,792 bytes** |
| Target vs rebuilt SHA-256 | `2b54ca3b…` **identical** |

**Established:** block-based learning correctly deduplicates a 72 MB artefact, the delta is **~1250× smaller** than the full artefact, and applying the patch **reconstructs the target byte for byte**, with the fingerprint verified on both sides.

## What stays open for M4-09

- **The installer is not signed** (`NotSigned`): neither a Windows Authenticode signature nor the manifest's optional Ed25519 signature, which is only exercised when `--signing-key` / `--public-key` are supplied explicitly.
- **No real installation** was performed. The ticket's exit criterion — "install on a clean machine, update from a previous version, uninstall without wiping the projects" — is **not** covered, and I did not simulate it: running the installer would modify the user's machine, which was not asked for.
- **The MSI was not built** in this pass (`-Bundle nsis` only).
- **Hosting, key rotation, the macOS/Linux matrix**: outside this campaign's scope.
- The sidecar is **not published** in the repository: the 72 MB installer is not committed either, only its traceability through the manifest is verifiable.

**M4-09 is therefore not closed.** This document replaces the absence of proof with a reproducible local proof of the build path and the delta chain, and names precisely what is missing.
