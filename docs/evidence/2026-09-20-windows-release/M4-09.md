## 1. Build de l'installateur NSIS

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/build-windows.ps1 -Bundle nsis
```

Le script enchaîne `npm run build` (frontend), `npm run tauri -- build --bundles nsis`, puis la génération et la **vérification** du manifeste. **Sortie : exit code 0.**

| Artefact | Taille | SHA-256 |
|---|---|---|
| `nsis/Muse-Desktop_0.1.0_x64-setup.exe` | **75 617 763 octets** (72,11 Mio) | `c8fcb5da1c2f49c3527e83e9f4791c068811a2fc8e45d67c439294221a6c30bd` |
| `nsis/Muse-Desktop_0.1.0_x64-setup.manifest.json` | — | schéma `muse-desktop.release-manifest.v1` |

**Vérifications indépendantes :**

- SHA-256 **recalculé** après coup : identique à celui du manifeste ;
- `verify-release-manifest.mjs` relancé à la main contre les octets réels → `{"valid": true, "errors": []}` ;
- métadonnées Windows de l'exécutable : `FileDescription: Muse-Desktop`, `ProductName: Muse-Desktop`, `FileVersion: 0.1.0`, `ProductVersion: 0.1.0` ;
- `CompanyName` **vide** ;
- **signature Authenticode : `NotSigned`.**

Le manifeste porte l'installateur **et** le sidecar avec leurs tailles et empreintes, sans chemin machine ni horodatage. Le sidecar n'étant pas versionné, ce manifeste relie l'installateur produit au binaire réellement fourni par l'environnement de build — c'est exactement son rôle.

## 2. Chaîne de mise à jour différentielle

Testée de bout en bout sur un cas réaliste : l'installateur réel, puis le même fichier augmenté d'une queue de 29 octets (simulant une nouvelle build).

```powershell
node scripts/release-delta.mjs create --from old.bin --to new.bin --output update.delta.gz
node scripts/release-delta.mjs apply  --from old.bin --patch update.delta.gz --output rebuilt.bin
```

| Mesure | Valeur |
|---|---|
| Source | 75 617 763 octets |
| Cible | 75 617 792 octets |
| **Delta produit** | **59 126 octets (57,7 Ko)** |
| Blocs modifiés | **1 sur 1154** |
| `useDelta` | `true` |
| Fichier reconstruit | **75 617 792 octets** |
| SHA-256 cible vs reconstruit | `2b54ca3b…` **identiques** |

**Établi :** l'apprentissage par blocs déduplique correctement un artefact de 72 Mo, le delta est **~1250× plus petit** que l'artefact complet, et l'application du patch **reconstruit l'octet près** la cible, empreinte vérifiée des deux côtés.

## Ce qui reste ouvert pour M4-09

- **L'installateur n'est pas signé** (`NotSigned`) : ni signature Authenticode Windows, ni la signature Ed25519 optionnelle du manifeste, qui n'est exercée que lorsque `--signing-key` / `--public-key` sont fournis explicitement.
- **Aucune installation réelle** n'a été exécutée. Le critère de sortie du ticket — « installer sur machine propre, mettre à jour depuis une version précédente, désinstaller sans effacer les projets » — n'est **pas** couvert, et je ne l'ai pas simulé : lancer l'installateur modifierait la machine de l'utilisateur, ce qui n'était pas demandé.
- **Le MSI n'a pas été construit** dans cette passe (`-Bundle nsis` seulement).
- **Hébergement, rotation des clés, matrice macOS/Linux** : hors périmètre de cette campagne.
- Le sidecar **n'est pas publié** dans le dépôt : l'installateur de 72 Mo n'est pas committé non plus, seule sa traçabilité par manifeste est vérifiable.

**M4-09 n'est donc pas clos.** Ce document remplace l'absence de preuve par une preuve locale reproductible du chemin de build et de la chaîne delta, et nomme précisément ce qui manque.
