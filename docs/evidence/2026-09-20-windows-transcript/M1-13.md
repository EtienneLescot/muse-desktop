# Fenêtre bornée du transcript sur 2 000 entrées — M1-13 (20 septembre 2026)

Mesure native dans la webview, via CDP, sur le sidecar Muse Windows natif 1.3.0.

## Mode opératoire

```powershell
$env:WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS = "--remote-debugging-port=9222"
npm run tauri -- dev
node scripts/cdp-long-transcript.mjs --entries 2000
```

Le script capture d'abord la valeur d'origine de la clé `muse-desktop.log.v1.<sessionId>` visée, écrit un journal de 2 000 entrées au **format réellement persisté** (`{clientMessageId, id, role, text, ts}`), recharge la page pour que l'hydratation de démarrage lise le nouveau journal, mesure, puis **restaure la valeur d'origine** dans un bloc `finally`.

## Résultat

| Mesure | Valeur |
|---|---|
| Entrées écrites | **2 000** (+ 1 entrée de graine conservée) |
| Journal visé | `muse-desktop.log.v1.01a0bea1…` (21 205 octets → 347 671 octets) |
| `data-entry-count` | **2001** |
| `data-window-start` / `data-window-end` | **0 / 160** |
| **Articles montés dans le DOM** | **160** |
| Nœuds DOM du journal (dont les 160 articles) | **967** |
| `aria-setsize` du premier article | **2001** |
| `aria-posinset` du premier article | **1** |
| `aria-label` / `aria-keyshortcuts` du journal | `Conversation messages` / `Home End PageUp PageDown` |
| `Load older messages` | absente — cohérent, la fenêtre est déjà à l'index 0, donc déjà sur les messages les plus récents |
| `Latest messages` présent | oui |
| `Find in conversation` présent | oui |

**Établi :** sur un transcript de 2 001 entrées, l'application ne monte que **160 articles** — exactement la borne documentée dans la roadmap (« fenêtre de 160 messages »). Le nombre total réel est exposé aux technologies d'assistance via `aria-setsize`, et la position globale via `aria-posinset` : la fenêtre bornée ne dégrade donc pas l'information sémantique.

Le coût DOM reste contenu : **967 nœuds** pour l'ensemble du journal, articles compris.

**Journal restauré** : la valeur d'origine (21 205 octets, 25 entrées) a été réécrite et vérifiée après la mesure.

## Chargement incrémental des anciens messages — mesuré

```powershell
node scripts/cdp-scroll-window.mjs --entries 2000
```

Le script écrit 2 000 entrées, recharge, puis met `scrollTop` à 0 — ce qui déclenche `onScroll` et son appel à `loadOlderMessages()` dès que `scrollTop < 120` — avant d'actionner le bouton **Load older messages** par un second chemin.

| Étape | Fenêtre DOM | Articles montés | `posinset` du 1ᵉʳ | `scrollHeight` | Nœuds |
|---|---|---|---|---|---|
| initial | **1840 – 2000** | **160** | 1841 | 174 694 | 970 |
| scroll 1 | **1720 – 1880** | **160** | 1721 | 165 478 | 971 |
| scroll 2 | **1600 – 1760** | **160** | 1601 | 156 238 | 971 |
| scroll 3 | **1480 – 1640** | **160** | 1481 | 146 998 | 971 |
| après le bouton | **1360 – 1520** | **160** | 1361 | 137 758 | 971 |

**Établi :**

- la fenêtre **recule de 120 entrées par chargement** — exactement la constante documentée (« 120 messages chargés à la demande ») ;
- le nombre d'articles montés **reste à 160** sur toute la séquence : le DOM **ne croît pas** avec les chargements successifs ;
- `aria-posinset` suit la fenêtre (1841 → 1361) : la position globale reste exacte pour les technologies d'assistance ;
- `scrollHeight` **décroît** à chaque étape (174 694 → 137 758), signature de la compensation d'espaces virtuels — le contenu au-dessus reste représenté, sa hauteur est recalculée ;
- le bouton **Load older messages** reste présent tant qu'il reste des entrées au-dessus.

Les deux chemins — **scroll** et **bouton** — produisent le même effet.

## Ce que ces mesures ne couvrent toujours pas

- **Le finder vers un résultat hors fenêtre** : `Find in conversation` est présent dans le DOM, mais le saut vers un résultat hors fenêtre n'a pas été exercé sur ces 2 000 entrées.
- **Les performances** (temps de rendu, mémoire) : non mesurées. La roadmap conditionne la virtualisation complète à « une mesure réelle de mémoire et de temps de rendu » — ces documents ne la remplacent pas.
- **La qualification assistive native** : non exercée.
- macOS / Linux : hors périmètre.

**M1-13 n'est donc pas clos**, mais son critère de mesure est désormais couvert pour la **borne du DOM** *et* pour le **chargement incrémental**.
