# Fenêtre bornée du transcript sur 2 000 entrées — M1-13 (20 septembre 2026)

Mesure native dans la webview, via CDP, sur le sidecar Muse Windows natif 1.3.0.

## Mode opératoire

```powershell
$env:WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS = "--remote-debugging-port=9222"
npm run tauri -- dev
node scripts/cdp-long-transcript.mjs --entries 2000
```

Le script capture d'abord la valeur d'origine de la clé `muse-desktop.log.v1.<sessionId>` visée, écrit un journal de 2 000 entrées au **format réellement persisté** (`{clientMessageId, id, role, text, ts}`), recharge la page pour que l'hydratation de démarrage lise le nouveau journal, mesure, puis **restaure la valeur d'origine** dans un bloc `finally`.

## Résultat

| Mesure | Valeur |
|---|---|
| Entrées écrites | **2 000** (+ 1 entrée de graine conservée) |
| Journal visé | `muse-desktop.log.v1.01a0bea1…` (21 205 octets → 347 671 octets) |
| `data-entry-count` | **2001** |
| `data-window-start` / `data-window-end` | **0 / 160** |
| **Articles montés dans le DOM** | **160** |
| Nœuds DOM du journal (dont les 160 articles) | **967** |
| `aria-setsize` du premier article | **2001** |
| `aria-posinset` du premier article | **1** |
| `aria-label` / `aria-keyshortcuts` du journal | `Conversation messages` / `Home End PageUp PageDown` |
| `Load older messages` | absente — cohérent, la fenêtre est déjà à l'index 0, donc déjà sur les messages les plus récents |
| `Latest messages` présent | oui |
| `Find in conversation` présent | oui |

**Établi :** sur un transcript de 2 001 entrées, l'application ne monte que **160 articles** — exactement la borne documentée dans la roadmap (« fenêtre de 160 messages »). Le nombre total réel est exposé aux technologies d'assistance via `aria-setsize`, et la position globale via `aria-posinset` : la fenêtre bornée ne dégrade donc pas l'information sémantique.

Le coût DOM reste contenu : **967 nœuds** pour l'ensemble du journal, articles compris.

**Journal restauré** : la valeur d'origine (21 205 octets, 25 entrées) a été réécrite et vérifiée après la mesure.

## Ce que cette mesure ne couvre pas

- **Le chemin de chargement des anciens messages** (`Load older messages` / préchargement au scroll) n'a pas été exercé : la fenêtre étant à l'index 0, il n'y avait rien à charger au-dessus. Le comportement documenté (« 120 messages chargés à la demande », compensation de hauteur) reste **non mesuré**.
- **Le finder vers un résultat hors fenêtre** : présent dans le DOM, non exercé sur ces 2 000 entrées.
- **La mesure de performance** (temps de rendu, mémoire) n'a pas été faite : seule la borne du DOM est établie.
- La roadmap conditionne la virtualisation complète à « une mesure réelle de mémoire et de temps de rendu » — cette mesure **ne la remplace pas**.
- macOS / Linux : hors périmètre.

**M1-13 n'est donc pas clos.** Son critère « mesure native à 2 000 entrées dans la webview empaquetée » est désormais satisfait pour la **borne du DOM** ; le chemin de chargement incrémental et la qualification assistive restent ouverts.
